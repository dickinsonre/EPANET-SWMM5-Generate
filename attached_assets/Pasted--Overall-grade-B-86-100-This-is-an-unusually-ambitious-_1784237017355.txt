# Overall grade: **B+ — 86/100**

This is an unusually ambitious and capable browser-based engineering application. For **education, synthetic model generation, solver benchmarking, and calibration exercises**, I would grade it **A−**. For use as a **production engineering/design tool**, I would currently grade it **C+/B−**, primarily because the validation and provenance do not yet match the strength of the “hydraulically valid” and “calibration-ready” claims.

I reviewed the public application and documentation, but did not conduct a source-code audit or independently run a large suite of generated models through native EPANET and SWMM executables.

# What the app does especially well

## 1. It solves a real educational and research problem

Generating synthetic networks is normally tedious. This application can produce repeatable EPANET or SWMM models across a very wide size range, expose the input file, generate a map and DEM, and create parameter ensembles. That is a strong value proposition for:

- Classroom exercises
- Hydraulic solver testing
- Calibration algorithm development
- Monte Carlo studies
- Software demonstrations
- Performance benchmarking
- Training people to read`.inp` files

The combination of seeded reproducibility, batch generation, node-count sweeps, Monte Carlo ensembles, GeoJSON, DEM, map export, and an in-browser solver is particularly strong. ([epanet-swmm-5-generate.replit.app](https://epanet-swmm-5-generate.replit.app/))

## 2. Reproducibility is treated as a core feature

The visible seed, copied configuration, locked seed option, configuration export, and documented PRNG are excellent. Reproducibility is essential for research and debugging, and many visual generators neglect it.

An even better implementation would attach a topology and parameter hash to every model, but the foundation is already good.

## 3. The engineering decision log is valuable

The detailed generation log is one of the best parts of the product. It explains:

- Why sources were placed
- Why pumps were added
- How pressure zones were created
- How pipe sizes were assigned
- Whether connectivity passed
- How demand and supply were estimated

That makes the generator less of a black box.

## 4. The export coverage is impressive

The application exposes standard`.inp` text and offers map, DEM, GeoJSON, configuration, batch, calibration, and report exports. It also documents a broad range of EPANET and SWMM sections. ([epanet-swmm-5-generate.replit.app](https://epanet-swmm-5-generate.replit.app/))

## 5. Progressive disclosure is present

The Simple/Advanced/Expert control is the right basic idea. Likewise, grouping controls under Network, Hydraulics, Environment, and Map & Export helps contain a very large feature set.

## 6. It uses appropriate official engines

SWMM 5.2.4 remains the latest release shown by the official EPA repository, while the latest OWA EPANET patch release shown publicly is 2.3.5. ([github.com](https://github.com/USEPA/Stormwater-Management-Model/releases))

# Highest-priority improvements

## P0: Make “validity” solver-gated

The largest product weakness is the gap between the wording **“hydraulically valid, calibration-ready”** and the workflow in which the solver still has to be loaded and run manually. The page can describe a generated network as connected and supply-adequate before a complete hydraulic or routing simulation has passed. ([epanet-swmm-5-generate.replit.app](https://epanet-swmm-5-generate.replit.app/))

Connectivity is necessary, but it does not prove hydraulic validity. A connected model can still contain:

- Negative pressures
- Unbalanced timesteps
- Pumps outside useful operating ranges
- Empty or overflowing tanks
- Conflicting valves
- Excessive velocities
- Unstable controls
- SWMM continuity errors
- Flooded nodes
- Conduit surcharge problems
- Invalid water-quality behavior

### Recommended validity levels

Use explicit, separate badges:

1. **Generated**
   Network objects and files were created.

2. **Syntax Validated**
   Required sections, references, IDs, curves, units, and values passed parser checks.

3. **Topologically Validated**
   All relevant nodes are connected to valid boundaries.

4. **Solver Passed**
   Native/WASM engine completed without fatal errors.

5. **Hydraulic QA Passed**
   Pressure, velocity, tank, pump, valve, convergence, and mass-balance criteria passed.

6. **Engineering Reviewed**
   Reserved for a model reviewed against user-supplied criteria—not something the generator should assign automatically.

The green “valid” presentation should appear only after the selected solver has run.

For models below a practical size threshold, automatically run the solver after generation. For very large models, ask:

> “Run full validation now? Estimated memory: 1.2 GB; estimated time: 18 seconds.”

---

## P0: Audit PRV units and terminology

The sample generation log describes a PRV setting as an HGL value, for example approximately “270 ft HGL.” That is potentially misleading.

In an EPANET input file, a PRV setting is downstream **pressure**—psi in a conventional US-customary model or meters in a metric model—not total hydraulic grade. ([usepa.github.io](https://usepa.github.io/EPANET2.2/back_matter.html?utm_source=openai))

The app may already convert the target HGL correctly when writing the INP, but the presentation should distinguish:

- **Target downstream pressure:** 50 psi
- **Downstream elevation:** 155 ft
- **Equivalent target HGL:** approximately 270 ft
- **EPANET PRV setting written to INP:** 50 psi

Add an automated test that parses every generated`[VALVES]` entry and confirms the written setting uses the correct pressure unit.

---

## P0: Show the exact engine build

The interface says “EPANET 2.3,” but the current official OWA release list identifies **EPANET 2.3.5** as the latest patch. That matters because recent patch releases corrected unit conversions, leakage computations, valve status behavior, and Toolkit operations. ([github.com](https://github.com/OpenWaterAnalytics/EPANET/releases))

Display something like:

> OWA-EPANET 2.3.5
> Git commit:`444725f`
> WASM build date: 2026-06-11
> Compiler: Emscripten x.x.x

For SWMM, similarly show:

> EPA SWMM 5.2.4
> Source tag:`v5.2.4`
> WASM SHA-256: …

If the app intentionally bundles base 2.3 rather than 2.3.5, update it.

---

## P0: Correct documentation inaccuracies and contradictions

The documentation states that EPANET “needs at least 3 points for a proper pump curve” or that three points are “required.” That is a good modeling recommendation, but it is not an EPANET format requirement. EPANET supports single-point, three-point, and multi-point pump curves; for a single-point curve it constructs the remaining curve using assumed shutoff head and maximum flow. ([usepa.github.io](https://usepa.github.io/EPANET2.2/3_network_model.html?utm_source=openai))

Use wording such as:

> “Three or more manufacturer or field-test points are recommended for defensible engineering analysis. EPANET also accepts a single design point and derives an assumed curve.”

There is also an internal control-rule contradiction: one section says the last matching rule wins, while another says equal-priority rules use the first-listed rule. The official behavior should be stated once, tested, and reused from a canonical documentation source.

### Add documentation tests

Create machine-readable facts and generate UI text from them:

```json
{
  "pump_curve": {
    "minimum_epanet_points": 1,
    "recommended_engineering_points": 3,
    "single_point_behavior": "EPANET derives an assumed curve"
  }
}
```

This prevents different documentation sections from drifting apart.

# Product and UX improvements

## 1. Replace the giant control panel with workflows

The application currently exposes an enormous number of controls. Even with collapsible sections, a new user has to understand network topology, terrain, demand allocation, pumps, pressure zones, infiltration, RDII, LID, groundwater, water quality, and simulation settings before feeling confident.

Introduce task-oriented entry points:

### Quick Start

- **EPANET teaching network**
- **EPANET calibration exercise**
- **EPANET solver benchmark**
- **SWMM stormwater network**
- **SWMM sanitary/RDII network**
- **SWMM LID demonstration**
- **Custom expert model**

Each workflow should ask only five to eight questions and place everything else under “Review assumptions.”

## 2. Make Simple mode genuinely simple

Simple mode should show approximately:

- Model type
- Size
- Units
- Terrain
- Demand or drainage intensity
- Number of sources/outfalls
- Simulation duration
- Seed
- Generate button

Advanced and Expert modes can expose the rest.

At present, the product appears to use progressive disclosure, but the overall page remains dominated by specialist controls and extensive embedded documentation. ([epanet-swmm-5-generate.replit.app](https://epanet-swmm-5-generate.replit.app/))

## 3. Create a clear four-step product state

The interface should visibly follow:

> **1. Configure → 2. Generate → 3. Validate → 4. Export**

Each stage should have one primary button.

Currently, generation, solver loading, quick simulation, report generation, exports, ensembles, and AI assistance compete for attention.

## 4. Add parameter search

Provide a command/search box:

> Search settings: “roughness,” “RDII,” “tank,” “report step”…

This would significantly improve Expert mode.

## 5. Add engineering tooltips with defaults and valid ranges

Every numeric field should expose:

- Definition
- Unit
- Typical range
- Current default
- Why it matters
- Whether it is directly written to the INP or used only by the generator
- Validation constraints

Example:

> **Manning’s n**
> Roughness coefficient for gravity conduit flow.
> Typical closed-conduit range: 0.011–0.015.
> Written to`[CONDUITS]`.

## 6. Show dependent parameters

If users change one parameter, identify affected outputs:

> “Changing reservoir head will trigger regeneration of source checks, booster pump sizing, pressure zones, and pump curves.”

The existing “settings changed—regenerate” warning is good, but it can be more specific.

## 7. Move the large technical textbook out of the main application

The embedded reference is impressive, but it substantially increases page density and makes the application feel like several products combined.

Split it into:

- **Generator**
- **Model inspector**
- **Documentation**
- **Tutorials**
- **Technical reference**
- **Validation methodology**

Keep contextual excerpts inside the app and open the full documentation in a separate route or panel.

# Engineering and validation improvements

## 1. Replace heuristic “supply adequacy” with clearer terminology

Reservoirs in EPANET are fixed-head boundary conditions and do not inherently have a finite capacity unless a capacity constraint is modeled separately. Therefore a displayed “supply capacity” for gravity reservoirs is a generator estimate, not necessarily a solver-established physical capacity.

Rename the metric:

> **Generator-estimated source capacity**

Then separately report:

- Simulated source flow at peak hour
- Source head
- Minimum network pressure
- Maximum source velocity
- Pump operating point
- Available storage
- Fire-flow result, if calculated

Avoid a single green S/D ratio implying comprehensive adequacy.

## 2. Validate the full EPS, not only time zero

A generated model can be fine at`T=0:00` and fail later.

For EPANET, automatically evaluate:

- Every hydraulic timestep converged
- Minimum and maximum pressure
- Negative-pressure count
- Pressure below target count
- Maximum velocity
- Maximum unit headloss
- Pump outside-curve warnings
- Pump cycling count
- Tank empty/full duration
- Tank recovery after 24 or 72 hours
- PRV state and downstream error
- Flow and demand balance
- Water-quality mass balance

For SWMM:

- Runoff continuity error
- Flow-routing continuity error
- Water-quality continuity error
- Flooding volume
- Surcharge duration
- Unstable node count
- Routing timestep reductions
- Outfall backwater behavior
- Conduit capacity exceedance
- Pump utilization
- LID mass balance

## 3. Add native-versus-WASM regression tests

For a fixed set of seeds and configurations:

1. Generate the same INP.
2. Run the WASM engine.
3. Run the official native engine.
4. Compare results within documented tolerances.

Test at least:

- Tiny EPANET DDA
- EPANET PDA
- EPANET EPS with tanks and controls
- EPANET chlorine
- SWMM dynamic wave
- SWMM groundwater
- SWMM RDII/DWF
- SWMM pollutants
- SWMM LID
- US and SI versions of each

Publish a validation matrix with the release.

## 4. Add property-based tests

Useful invariants include:

- Every referenced node, link, curve, pattern, and timeseries exists.
- Every pipe has different start and end nodes.
- Every pump curve decreases with increasing flow.
- Tank minimum level ≤ initial level ≤ maximum level.
- All generated coordinates and numeric properties are finite.
- All junctions are reachable from a source where required.
- All SWMM drainage outlets exist.
- Subcatchment areas are positive.
- Shape parameters are legal for the selected cross section.
- Unit conversion to SI and back preserves values within tolerance.
- Same seed and configuration produce identical hashes.
- Monte Carlo “fixed topology” ensembles have identical topology hashes.

## 5. Add round-trip compatibility testing

Every release should test:

- Generate INP
- Parse with the official engine
- Export or normalize
- Re-import into the generator
- Compare object counts and critical parameters

Also maintain tests for WNTR and PySWMM compatibility.

## 6. Include a model manifest

Every exported model should include a machine-readable manifest:

```json
{
  "generatorVersion": "4.0",
  "engine": {
    "name": "OWA-EPANET",
    "version": "2.3.5",
    "commit": "444725f"
  },
  "seed": 42,
  "units": "GPM",
  "configHash": "...",
  "topologyHash": "...",
  "generatedAt": "...",
  "validation": {
    "syntax": "pass",
    "connectivity": "pass",
    "solver": "pass",
    "eps": "warning"
  }
}
```

Put this in batch ZIPs and optionally summarize it in`[TITLE]`.

- Input properties
- Generated rationale
- Time-series results
- Warnings
- Connected elements
- INP line or section
- Copy ID

Every color map needs:

- Units
- Minimum and maximum
- Classification method
- Timestep
- Missing/invalid value color
- Threshold indicators

Never rely on a red-to-green scale alone.

## 3. Add engineering queries

Examples:

- Nodes below 20 psi
- Nodes above 80 psi
- Pipes above 5 ft/s
- Pipes above 10 ft/1,000 ft headloss
- Pumps outside preferred operating range
- Flooded SWMM nodes

The official EPANET interface similarly supports map-based examination of node and link results, so this would be consistent with established workflows. ([usepa.github.io](https://usepa.github.io/EPANET2.2/7_map.html?utm_source=openai))

## 4. Improve the HGL profile

Allow users to select endpoints rather than always using the lowest-to-highest elevation path. Include:

- Ground elevation
- Hydraulic grade
- Pressure band
- Pipe crown/invert
- Pump head additions
- Valve losses
- Tank and reservoir levels
- Minimum pressure threshold
- Animation across time

- Do not communicate pass/fail only through green and red.
- Provide patterns or symbols in addition to color.
- Ensure all controls are keyboard accessible.
- Add visible focus indicators.
- Associate every label with its input.

# Performance and architecture improvements

## 1. Keep the single-file release, but not the single-file source architecture

A single downloadable HTML artifact is excellent for distribution. However, the development source should be modular:

```text
/src/generation/epanet
/src/generation/swmm
/src/validation
/src/solvers
/src/export
/src/map
/src/ui
/src/docs
/tests/golden
/tests/property
```

Compile these modules into the single-file offline release.

## 2. Use Web Workers

Generation, solver execution, ZIP creation, DEM interpolation, and large canvas rendering should occur outside the main UI thread.

Add:

- Cancel button
- Progress by stage
- Estimated memory
- Estimated remaining time
- Worker crash recovery

## 3. Add safe size limits based on device capability

Before creating a 50,000- or 100,000-node model, inspect available memory and warn users:

> “This model may require approximately 2.4 GB during generation and export.”

Offer:

- Lower-resolution map
- Skip INP preview rendering
- Skip Voronoi
- Stream ZIP
- Generate without city buildings
- Generate topology only

## 4. Virtualize large text and tables

Do not put a 100,000-node INP or full result table directly into the DOM. Use:

- Virtual scrolling
- Search by object ID
- Section navigation
- Download-only mode for very large output
- Worker-based text search

# Documentation and trust improvements

## 1. Separate facts, defaults, heuristics, and recommendations

Use visual labels:

- **Engine requirement**
- **Generator default**
- **Engineering recommendation**
- **Illustrative assumption**
- **Regulatory value—verify locally**

This matters because the documentation currently mixes official EPANET behavior, general engineering practice, local regulations, rules of thumb, and generator assumptions.

## 2. Add citations beside individual technical claims

Statements involving AWWA, NFPA, EPA, state pressure requirements, chlorine residuals, calibration tolerances, transient-analysis triggers, velocity limits, software pricing, or product capabilities should have precise citations and publication dates.

Avoid presenting broadly varying values as universal requirements.

## 3. Tone down the comparison table

The competitor table is attention-grabbing, but claims such as exact software pricing, platform limitations, add-on requirements, and feature absence can quickly become outdated or disputed.

Use:

> “Indicative comparison as of July 2026; verify with vendors.”

Better still, focus the table on objectively testable generator capabilities.

## 4. Clarify branding and endorsement

Themes named for EPA, universities, and commercial companies could imply affiliation or endorsement. Add a visible disclaimer:

> “Theme names are visual presets only. This project is not endorsed by or affiliated with the named organizations.”

Do the same for logos, colors, testimonials, and historical accounts. A signed first-person account should link to its original authorized publication or state that it is reproduced with permission.

## 5. Clarify AI privacy and cost

Before sending anything to the AI assistant, show:

- Exactly what data will be sent
- Whether coordinates, labels, configuration, or results are included
- Estimated credit usage
- Model/provider
- Retention policy
- A preview of the payload
- A clear consent button

“Only sees a summary” is a good start, but users should be able to inspect that summary.

# Recommended release roadmap

## Next release: credibility and correctness

1. Update or identify exact EPANET patch version.
2. Audit PRV settings and displayed units.
3. Correct pump-curve and control-rule documentation.
4. Replace “hydraulically valid” with tiered validation badges.
5. Auto-run validation for small and medium networks.
6. Add exact solver errors and warnings to the Stats tab.
7. Add engine commit and checksums to exports.
8. Add branding and engineering-use disclaimers.

## Following release: UX and accessibility

1. Introduce task-based Quick Start workflows.
2. Simplify Simple mode.
3. Add settings search.
4. Add node/link inspector.
5. Add accessible result legends and data tables.
6. Separate the long textbook documentation from the generator workspace.
7. Conduct WCAG 2.2 AA testing.

## Longer-term: defensibility

1. Publish native-versus-WASM regression results.
2. Add property-based and unit-conversion tests.
3. Publish golden models and expected outputs.
4. Add manifest and topology hashes.
5. Add uncertainty distributions and sensitivity analysis.
6. Support user-defined acceptance criteria.
7. Publish a formal validation methodology and release changelog.

# Bottom line

This is already an **excellent synthetic network generator and educational platform**. Its feature set is closer to a small modeling laboratory than a simple generator. The biggest opportunity is not adding more features—it is making the existing features **more defensible, easier to navigate, independently testable, and more precise in their claims**.

If the next version concentrates on solver-gated validation, exact engine provenance, documentation correction, workflow simplification, and accessibility, I would expect the overall product grade to move from **B+ to A−/A**.
